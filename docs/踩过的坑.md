# 踩过的坑

README 里只留了最狠的三条。这里是完整的，按踩到的顺序，都是真机上撞出来的。

## 一、两边同时写同一份文件，必撞冲突

同步盘看到两边各改了一份，会挑一个赢，输的那份顶进 `xxx.sync-conflict-日期-随机.md`。读端不认这个文件名，信就静默丢了——不报错，不告警，你以为发出去了。

**治得住的那一半**：按写者分文件，`信箱-alice.md` 只有 alice 写，`信箱-bob.md` 只有 bob 写。正文追加撞不着了。

**治不住的那一半**：标 `[x]` 得改对方那份文件——这是「谁办完谁标」的代价。今天实测撞过两次（17:49、21:24），各留一个冲突副本。**冲突副本是这条规矩的常数，不是意外。** 所以读端必须扫 `信箱*.sync-conflict-*.md`，把它当常态处理；标完拿备份 diff 核，别看错文件。

**补丁**：读端把 `信箱*.sync-conflict-*.md` 也扫一遍。只是补丁——冲突文件里的条目归属会丢，你不知道它是给谁的。

## 二、读文件要防半截

同步盘落盘是「先写临时文件再改名」，中间有窗口。跟得太紧会读到空文件或者半行。

**做法**：连续读三次一致才算数；空文件且文件非空则隔一秒重读。别只读一次就信。

## 三、`node --check` 过了不等于能跑

它只查语法。漏一个 import、错一个函数名、少一个 await，语法全对，要等定时器响第一声才炸。

**做法**：写个冒烟脚本。假 ctx 跑 `apply()`，把每个定时器手动拨响一次，真调用一遍。见 `test/smoke.mjs`。

## 四、验证要验「抓得住」

测试全绿不等于测试有用。八个用例全过，可能因为八个都没真跑到。

**做法**：故意弄坏一处——删一个 import、把版本判断改成只认 `v99`、把校验值改成全零——看它报不报错、退出码是不是非零。它不报，你的测试就是装饰。

**假通过比没验更危险。**

## 五、热重载会再跑一遍 `apply()`

插件热重载（dispose 旧 fiber、重新 import、再 `ctx.plugin()`）会让 `apply()` 在同一个进程里跑第二遍。第一遍里 `setTimeout(() => start(), 10000)` 没清掉，十秒后第二个守护就起来了，两个 watcher 抢同一份文件。

**做法**：把定时器句柄挂到 `globalThis`，新一轮 `apply()` 开头先 `clearTimeout`。光加一个「已经起过」的开关挡不住——`start()` 还是会跑。

**验法**：热重载之后，日志里「启动」只该出现一行。

## 六、`?v=时间戳` 只重载入口模块

`await import(\`${import.meta.url}?v=${Date.now()}\`)` 只让入口文件重跑一遍，它 import 的相对子模块还是旧缓存。

**做法**：插件写成单文件；或者改子模块时老实重启。别指望热重载能救全部。

## 七、`pkill -f` 不一定清得干净

`pkill -f mailboxd` 发完信号，进程可能还活着，占着端口。新进程起不来，网页一直 403「没有口令」，而 `run.log` 里打的是新口令——两边对不上，看着像口令错了，其实是旧进程在答。

**做法**：`pkill` → 等 2 秒 → `pkill -9` → 等 1 秒 → `pgrep` 确认干净，再起。

**别用太宽的匹配**：`pkill -f mailboxd` 会把 `vim ~/mailbox/mailboxd.mjs` 一起杀掉。用 `pgrep -f 'node .*mailboxd\.mjs'` 收窄。

## 八、`agent.followup` 不一定在 `agent` 上

不同引擎的会话对象长得不一样。我们在这上面栽过一次：`ctx.agents.get()` 拿到的东西没有 `followup`，正确路径是 `ctx.get('sessionController').resolveAgent(会话号)`，返回 `{agent}` 或 `{error}`，拿到 `agent` 才有 `followup`。

**教训**：别照抄 API 名字，去源码里看那一条链路上到底是谁的方法。
