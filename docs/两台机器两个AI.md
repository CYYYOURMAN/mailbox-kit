# 实操：让两台机器上的两个 AI 互相叫醒

这是这套东西真正跑起来的样子。不是设计稿，是一天里从零搭通、边跑边改的记录。

场景：一台 Windows 电脑，一台安卓手机，各跑一个 AI 助手。中间隔着一个同步盘。

想要的效果：**手机那边写一行字，电脑这边几秒内自己醒过来干活；反过来也一样。**

## 一、要备什么

- 两台机器，各有一个能装插件的 AI 助手（这里用的是 DeepSeek Harness，别的引擎照着换适配层就行）。
- 一个双向同步的目录（这里用 Syncthing，iCloud、OneDrive、坚果云也能当信箱，慢一点）。
- 一个两边都能写的目录，比如 `notes/`。

不需要：服务器、公网 IP、端口、账号体系。

## 二、七步搭起来

1. **把同步目录挂上。** 两边指向同一个 folder，双向同步。先拿一个测试文件确认几秒能同步过去，再往下走。
2. **定信箱文件名。** 两边各写一份，只写自己那份：
   - 电脑写 `信箱-电脑.md`，手机读；
   - 手机写 `信箱-手机.md`，电脑读。
   文件名按写者分，物理上就不可能撞车。
3. **定一行的格式。** 一行一件事：

   ```
   - [ ] 18:27 电脑→手机：冒烟脚本给过来了，跑一遍把结果写我这儿
   ```

   `[ ]` 没办、`[x]` 已办。**谁写的谁标**，读的人不改别人的文件。
4. **装核心。** `npm i mailbox-kit`，或者直接把仓库拉下来。
5. **写适配层。** 三十行左右，只做三件事：拿到会话、把文字塞进去、看它醒没醒。（`adapters/dsh-engine.example.js` 是照抄的模板。）
6. **两边各起一个守护。** 盯同步目录，看见自己该读的那份有新行，就去重、攒批、叫醒。
7. **验。** 一边写一行，掐表，看另一边几秒醒。

## 三、实际不是这么顺

上面那七步是回头理出来的。真走的时候长这样，一步一坑：

- **一开始** 先把三个平台的读取脚本从手机挪到电脑跑通，才敢碰互通这件事。
- **第二步** 想的是「定时轮询问信箱」，聊到要不要为它烧 token，否了。
- **第三步** 写了第一版：PowerShell 脚本、Windows 计划任务十分钟一次、有新信就弹个气泡。能用，但只能叫醒人，叫不醒 AI。
- **换个做法** 换成插件：跑在引擎里面，直接往会话里塞消息。
- **装上，第一次真投就报错**：`TypeError: agent.followup is not a function`。拿错了对象——该走 `sessionController.resolveAgent()` 拿 agent，不是 `ctx.agents.get()`。翻宿主的源码才对上。
- **改对，通了。**
- **接着撞车**：我和它同时往同一个信箱文件写，同步盘判冲突，我那封信被顶进 `信箱.sync-conflict-…md`，主文件里没了，插件不读那个文件名——**信静默丢了，谁都不知道**。
- **拆成两份**，各写各的。这不是补丁，这是根治。
- **然后** 把「每十五秒读一遍」改成「盯目录，文件动了就读」，本机三秒。
- **第一次跨机真跑**：端到端 **29 秒**。三秒在叫醒，二十六秒在同步盘搬家。
- **再往后** 把能通用的部分拆成这个仓库，引擎相关的留成薄薄一层适配。
- **它拿到代码**，挑出两个真 bug（就是第四节那两个）。
- **中间走了一段死路**：想让程序自己重启自己。写了插件、试了三次——`CloseMainWindow` 返回 True、`taskkill` 说「成功发送终止信号」，进程都不退，每次只能硬关。改成一键 bat，我自己点了一次，**App 直接崩了**。叫停了，全删。这段现在一行代码都不剩，只留教训在下面第六节。
- **最后** 把同步盘的文件监听延迟从 10 秒改成 2 秒。端到端从 29 秒掉到 5–7 秒。

一天里删掉的东西，比留下的多。留下的是能跑的那条路。
## 四、真跑出来的数

| 环节 | 数 |
|---|---|
| 本机文件落盘 → 插件投出去 | 1.5 – 3 秒 |
| 顺手写的信，端到端（改同步参数前） | 29 秒 |
| 端到端（把同步盘的文件监听延迟从 10 秒调到 2 秒后） | **5 – 7 秒** |
| 两边兜底轮询（watch 挂了才轮到它） | 60 秒 |

那 29 秒里，真正花在「醒」上的只有三秒，剩下全在同步盘搬家上。它默认故意等十秒攒一批再扫。目录里就几个小文件，攒的意义不大——改成两秒，端到端直接掉到五秒出头。

**这一刀比优化代码值。** 先量，再改，别猜。

## 五、两个 AI 怎么互相改 bug

这是意外收获。信箱一通，两个 AI 之间不用人转话了。

真实发生过的三轮：

1. **我发代码，它看。** 它挑出两个真 bug：
   - 目录监听的过滤只认 `inbox-` 前缀，可实际文件叫「信箱-手机.md」，事件全被丢掉，监听等于白装；
   - 指纹库用「里面有几条」判断建没建过档，首跑零条就每次重启都重来，正好把刚到的那封信当旧账吞掉。
   两个都是我自己看三遍看不出来的。
2. **我改，它验。** 改完把结论写回信箱，它拉到代码再跑一遍。
3. **它把验法升级了。** 我给了一个冒烟脚本，它没只跑「过」，而是**故意删掉一个 import 再跑**——要确认脚本真能抓到毛病。它报了 `ReferenceError`、退出码 1。这一步我没做，是它补的。

**结论：验证要验「抓得住」，不能只验「过得去」。** 假通过比没验更危险。

## 六、六个坑，按踩到的顺序

1. **别两边同时写同一份文件。** 同步盘会判冲突，文件被顶进 `xxx.sync-conflict-日期-随机.md`。你的读端不认这个文件名，信就静默丢了。按写者分文件是唯一的根治办法，扫冲突文件只是补丁。
2. **读文件要防半截。** 同步盘落盘是「先写临时文件再改名」，中间可能读到空文件或者半行。连续读三次一致才算数。
3. **`node --check` 过了不等于能跑。** 它只查语法。漏一个 import、错一个函数名，要等定时器响第一声才炸。写个冒烟脚本：假 ctx 跑 `apply()`，再把每个定时器手动拨响一次。
4. **改完代码想不重启就换上（热重载），小心定时器。** `apply()` 会在同一进程里跑第二遍，里面没清的 `setTimeout(() => start(), 10000)` 十秒后把第二份守护拉起来，两个 watcher 抢同一份文件。句柄挂 `globalThis`，新一轮开头先 `clearTimeout`。
5. **别指望「温和关闭」在 Electron 应用上管用。** 试过 `CloseMainWindow` 返回 True、`taskkill` 说发送成功，进程都不退——它八成拦了退出信号或者关窗即最小化到托盘。要退就硬关，而且要接受「这条命令可能把自己也杀了」。
6. **不在同一个进程里起进程，有时候起不来还不报错。** `spawn(..., { detached: true })` 在某些宿主里静默失效。要独立进程就让系统去起（计划任务 / 快捷方式），别在宿主自己的进程树里绕。

## 七、这套东西适合谁

- 手上有两台机器、两个助手，想让它们自己接活的。
- 网络不通、没有公网服务、也不想开端口的。
- 想让 AI 写的字留成文件，随时能翻、能改、能版本管理的。

不适合：要高实时（毫秒级）的、要传大量二进制的、要多人同时协作的。它是留言板，不是电话。

还有一条：这套东西只在 Windows 和 Linux 上真跑过。Mac 那段弹窗代码写了，没机器验，别当它一定是好的。
